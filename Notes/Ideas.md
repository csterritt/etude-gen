## Etude Generator

The main ideas here are:

- This is a web application, with full user authentication and session management
- Users must sign in to use the application
- I want to generate music for the piano as a student; there is no separate teacher interface

### User form flow

- The user should be able to select a number of parameters for the music generation.
  - These parameters are stored in a D1 database table called `etude_params`
  - There can only be one active set of parameters at a time per user
  - The forms below use the POST-redirect-to-GET pattern
  - The music should be generated by a process of the user specifying via a series of forms. Each form submission updates the database, and shows answers from earlier forms:
    - First:
      - Number of measures, from 4 to 32
      - The time signature (for now, only 2/4, 4/4, 3/4)
      - The key to play in from the supported keys (major or minor, up to four flats or sharps)
      - One or more octaves (from octave 2 to 6)
      - Hand (left, right, both)
    - Second:
      - Pitches from the chosen key and octave(s) (e.g., "A4", "Bb5", "C3", "D#6", etc.)
        - These should be presented as a list of checkboxes, with the user able to select one or more, with a "Select all" button
      - Durations (for now only eighth, quarter, half, whole, dotted half, dotted quarter), limited to those which will fit in the chosen time signature
    - Third, when generating two-hand pieces:
      - Split point for all the available pitches, so that the pitches below the split point go to the left hand and the pitches above the split point go to the right hand. There must be at least one pitch in each hand.
  - Finally:
    - Present a summary for user approval. There should be 'Back' buttons on each step to allow the user to go back and change their selections, and a 'Generate' button to generate the music as a web page, and (on the generated music page) a 'PDF' button to generate a PDF for download.
  - The web page with the generated music from the server will still have the summary form at the top, with all the user's choices shown, so that the user can go back and change their selections. There will be a "Start a new piece" button to clear the current parameters and start over. It will also have a separate form with a 'PDF' button that will submit that form to generate the PDF with the same music.

### Internal structure generation

- The music should then be generated randomly from the list of notes, durations, octaves, and hand(s) selected
  - The music should not be totally random:
    - There should be occasional repeated one-bar phrases
    - Probabilities of intervals in half-steps: (which sum to 1.0)
      - 0: 0.0932197441181743
      - 1: 0.0755079927357212
      - 2: 0.121143267210103
      - 3: 0.109028940489093
      - 4: 0.0981260464401835
      - 5: 0.0883134417961651
      - 6: 0.0794820976165486
      - 7: 0.0715338878548937
      - 8: 0.0643804990694044
      - 9: 0.0579424491624639
      - 10: 0.0521482042462175
      - 11: 0.0469333838215958
      - 12: 0.0422400454394362
  - All the possible rhythms have been generated and are in the Notes/all-rhythms.txt file. Each list is preceeded by a time signature. Then the possible rhythms for that time signature are listed, one per line, with the following note lengths represented by the following characters:
    - `W` = whole note
    - `H` = half note
    - `D` = dotted half note
    - `Q` = quarter note
    - `R` = dotted quarter note
    - `E` = eighth note
  - The patterns containing unselected duration tokens are excluded from the possible rhythms
  - For each hand, a list of bars should be generated
    - 20% of the time past the first bar, a bar should be a duplicate of a previous bar
    - Each bar for each hand that is not a duplicate should be generated in the following way:
      - Choose a rhythm from the possible rhythms for the chosen time signature
      - The initial note will not have a pitch yet
      - For the first bar, choose a random pitch from the user's selected pitches for the current hand (or a Rest), and assign that pitch to the first note. For bars past the first, remember the pitch chosen for the last note of the previous bar
      - Loop over the rest of the notes in the bar, assigning a new pitch to the next note, by looking at all the notes in the current hand's range and randomly selecting one by using the interval probabilities. Intervals can be up or down. 10% of the time generate a rest instead of a pitch. A rest can follow another rest, but only if it's a different duration. After a rest, the next note should be chosen randomly from the current hand's range.
    - If both hands need to be generated:
      - Go through the same process for the second hand, but use the second hand's pitch list
      - For any bar of the second hand:
        - 25% of the time, use the same rhythm for the second hand as is in the corresponding bar of the first hand, but picking different pitches, except rests should be copied into the same position in the bar
        - 75% of the time, choose a new random rhythm
      - Either way, do the same type of pitch generation for the second hand's bar, using its range
- The music should be stored internally in a presentation-independent way.

### LilyPond generation

- The generated music should:
  - Have sheet music style images generated by lilypond (https://lilypond.org) using the current stable release
    - The notes will be on a grand staff with treble and bass clefs
    - The time signature will be shown
    - Notes played by the right hand should have stems pointing up
    - Notes played by the left hand should have stems pointing down
    - The server will invoke the lilypond web application via a separate web application, accessed via HTTP POST with a JSON body containing the LilyPond code, and a Bearer token for authentication. It will return an SVG of the sheet music or an error message.
    - The server will embed the SVG in the page returned to the browser, after sanitization with the DOMPurify and jsdom libraries.
  - The returned page will contain the full final form with all user choices presented, and the same form for generation with hidden fields documenting the user's choices.
  - All form values will be validated by the server and appropriate error messages returned to allow the user to correct any invalid input.
  - The server will limit the user to one successful etude generation per minute. Separately, successful PDF generation will be limited to one per minute as well, but tracked separately so the user can generate a PDF right after getting the web page version.

### Data structures

- The internal music representation should be a JSON-serializable hierarchical structure: Piece → Measures → Notes.
  - Piece contains an array of measures.
  - Each measure contains one or two arrays of notes (one for right hand, one for left hand). If there is only one hand being generated, the other array should be empty.
  - Each note has: pitch and duration info.
- For generation, the server will turn the internal representation into LilyPond code, and send it to the Lilypond generator API.

Changes from base auth app:

### Environment Variables

- `LILYPOND_SERVICE_URL` (secret) — base URL of the external LilyPond service.
- `LILYPOND_API_KEY` (secret) — bearer token for the external service.
- `LILYPOND_TIMEOUT_MS` (var, default 30000) — timeout for external service calls.

### Paths

- `/etude` - GET — main etude generation page
- `/etude` - POST — generate etude
- These replace the '/private' in the base auth app

### Lilypond generator API

- The Lilypond generator API is a separate web application, accessed via HTTP POST by the server to `/generate` with a JSON body containing the LilyPond code, and a Bearer token for authentication. It should return an SVG of the sheet music, or an error message. Alternatively, it can do an HTTP POST to `/pdf` with the same body, and return a PDF or an error message.
- There will be a timeout of 30 seconds for the LilyPond generator API calls.
- Errors returned, either from the API or from the server, will be reported to the user.

### Logging

All errors should be logged with a request/correlation identifier, but no PII or secrets, for diagnosis.

### Accessibility

The forms and generated sheet music require explicit accessibility behavior. At minimum, the PRD should require labeled form controls and validation errors, focus management after errors or generation, and a useful text alternative or description for the generated score. The SVG must not introduce inaccessible or unsafe interactive content.
