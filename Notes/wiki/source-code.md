# Source Code

A catalog and summaries of all source files under `src/`.

## lib/

### config-validator.ts

Validates the etude feature's required configuration bindings in one pass, collecting every defect rather than failing on the first. Checks the D1 binding (`PROJECT_DB`), the private R2 binding (`ETUDE_GEN_STORAGE`), `LILYPOND_SERVICE_URL`, `LILYPOND_API_KEY`, and `LILYPOND_TIMEOUT_MS`. The timeout defaults to 30,000 milliseconds when absent and must be a positive finite number when present. Defect messages name the affected value but never include resolved secret values. Exports `validateEtudeConfig`, `DEFAULT_LILYPOND_TIMEOUT_MS`, and the `ConfigDefect` / `ConfigValidationResult` / `EtudeConfigInput` types.

### correlation-id.ts

Generates a fresh UUID v4 correlation identifier per call using the platform `crypto.randomUUID()` (available in the Cloudflare Workers runtime and in Node/Bun). Focused on generation only — middleware, header, and logging behavior live elsewhere. Exports `generateCorrelationId`.

### logger.ts

Structured logging utility that redacts sensitive data. `logInfo`, `logError`, and `logWarn` serialize a JSON line with `level` and `message`, then run the context through `redactContext` before serialization. Sensitive keys (names, email, session/token/secret/key/authorization/bearer/credential/password fields, and LilyPond request bodies) are replaced with `[REDACTED]`; the `correlationId` key is passed through verbatim so a log line can be traced to its request or operation. `sanitizeError` preserves the existing error-shrinking behavior. `logRoutineSuccess` is a no-op: per the project logging policy, routine successful operations are not logged merely for completeness — only failures, refusals, and cleanup outcomes are logged. Exports `redactContext`, `sanitizeError`, `logInfo`, `logError`, `logWarn`, `logRoutineSuccess`.

### correlation-context.ts

Defines the typed correlation context that threads a request's correlation identifier into every Workflow Service operation, renderer call, repository call, and artifact-store call, and into deferred work that outlives the response. A `CorrelationContext` carries a `correlationId` and a `kind` discriminator (`'request' | 'operation'`) so an operation-originated line is distinguishable from a request-originated one. `createRequestCorrelation` wraps an existing identifier; `createOperationCorrelation` generates a fresh UUID v4 when none is supplied, modelling deferred work with no remaining request context. The four service interfaces (`WorkflowService`, `Renderer`, `Repository`, `ArtifactStore`) are contracts that later issues fill with real behavior; this slice provides typed surfaces and trivial recording stubs (`makeWorkflowServiceStub`, `makeRendererStub`, `makeRepositoryStub`, `makeArtifactStoreStub`). `runDeferredCleanup` carries forward an originating request context, or generates a labelled operation identifier when none remains.

### refusal-logger.ts

Logs lost-lock, stale-operation, stale-epoch, and stale-Piece refusals with a typed category and enough context to diagnose them without logging user identifiers, Piece content, LilyPond source, grant identifiers, or credentials. Defines a `RefusalCategory` string-literal union and a `RefusalContext` carrying only safe fields (`category`, `correlationId`, optional `reason`); `logRefusal` emits one structured warning line via the redacting `logWarn`, passing only the safe fields through. The refusal decisions themselves are owned by later issues. Exports `RefusalCategory`, `REFUSAL_CATEGORIES`, `RefusalContext`, `logRefusal`.

### etude-params-repository.ts

Repository for the `etude_params` aggregate, encapsulating the physical Drizzle columns behind a domain `EtudeParams` interface. `loadOrCreateEtudeParams(db, userId)` atomically inserts a default aggregate or loads the existing one — the caller that loses the insert race handles the UNIQUE-constraint violation on the owner reference as a load of the winner's aggregate, not as an error (the violation is detected across both the D1 and bun-sqlite drivers, which surface it with different error shapes). `loadEtudeParams(db, userId)` is an owner-scoped read returning `null` when none exists. `updateEtudeSetup(db, userId, expectedEpoch, expectedWorkflowVersion, values)` conditionally updates the setup-step fields (measure count, time signature, hand, key signature, selected octaves) using a compare-and-set on both `aggregateEpoch` and `workflowVersion` (Issue 10): the function first loads the current aggregate to compare the submitted values against the stored ones — when every submitted value is identical (including the normalized octave string) AND the expected version matches, the request is a no-op (no version increment, no write, no flag changes), avoiding spurious version bumps from a double submission of the same form; a stale version on an identical resubmit is still a `version-mismatch`. Otherwise it performs a single conditional Drizzle `update` with a `where` clause matching `userId`, `aggregateEpoch === expectedEpoch`, and `workflowVersion === expectedWorkflowVersion`, so a request whose captured epoch or version no longer matches the stored values updates zero rows. On a zero-row update the function re-loads the current row to disambiguate the conflict kind: if the stored `aggregateEpoch` no longer equals `expectedEpoch`, it returns `{ kind: 'epoch-mismatch' }`; otherwise it returns `{ kind: 'version-mismatch' }` (covering older, newer, and tampered values uniformly). A missing aggregate is a safe `version-mismatch`, never a 500. On success the same committed transition increments `workflowVersion` by 1, sets `setupConfirmed` to true, and updates the measure/meter/hand/key/selected-octaves columns. The `selectedOctaves` column stores the normalized ascending octave selection as a comma-separated string (e.g. `'2,4,6'`). The same transition applies the Issue 11 dependent-downstream invalidation plan computed by `computeDownstreamInvalidation` (from `src/lib/etude-invalidation.ts`): depending on which upstream fields changed, the plan clears the dependent downstream data fields (`selectedPitches`, `selectedDurations`, `splitBoundary` to null) and confirmation flags (`notesConfirmed`, `splitConfirmed` to false) while retaining unrelated downstream state — there is no second, separate transition (cross-cutting contract section 4). The `EtudeParams` domain interface includes the three nullable downstream data fields (`selectedPitches`, `selectedDurations`, `splitBoundary` as `string | null`) added in Issue 11; these hold the pitch-selection, duration-selection, and split-boundary data written by the notes and split steps (Issues 13, 14, 16) and are null until a step (or a test) writes them. `loadOrCreateEtudeParams` and `loadEtudeParams` follow the `withRetry`/`toResult` Result-returning pattern from `src/lib/db-access.ts`; `updateEtudeSetup` does not use `withRetry` because CAS conflicts are deterministic and retrying them would lose the typed conflict information. The default aggregate carries the PRD's practical defaults (8 measures, 4/4, C major, selected octaves `'4'`, octave range 4, right hand), `workflowVersion` 1, `aggregateEpoch` 1, all three step-confirmation flags (`setupConfirmed`, `notesConfirmed`, `splitConfirmed`) false, and all three downstream data fields null. `updateEtudePitches(db, userId, expectedEpoch, expectedWorkflowVersion, selectedPitches)` is the Issue 13 pitch-only CAS save: it conditionally sets `selectedPitches` and increments the version, with the same identical-resubmit short-circuit, stale-version/epoch disambiguation, and `db-error` wrapping as `updateEtudeSetup`; it does NOT set `notesConfirmed` (the notes step is confirmed only when both halves are confirmed) and does not touch durations or split state. `updateEtudeNotes(db, userId, expectedEpoch, expectedWorkflowVersion, selectedPitches, selectedDurations)` is the Issue 14 combined CAS save: it conditionally sets `selectedPitches`, `selectedDurations`, and `notesConfirmed: true` in one transition (confirming the coherent notes step — both halves confirmed in this commit) and increments the version, with the same CAS conflict and short-circuit semantics; it does NOT modify `splitBoundary`, `splitConfirmed`, or `setupConfirmed`. Exports `EtudeParams`, `EtudeUpdateError`, `loadOrCreateEtudeParams`, `loadEtudeParams`, `updateEtudeSetup`, `updateEtudePitches`, `updateEtudeNotes`.

### pitch-selection-validator.ts

Pure functions encoding the Issue 13 pitch-selection rules. `validatePitchSelection(submitted, available, hand)` enforces the cardinality minimums — at least one pitch for one-hand mode (`'left'` or `'right'`) and at least two for two-hand mode (`'both'`) with the exact field-level message `"Select at least two pitches when using both hands."` — and rejects any submitted pitch not in the derived available set, naming the unavailable pitch. It tolerates hostile shapes (a non-array, duplicates, reordered values, an empty array) deterministically without throwing: a non-array yields an empty array (zero pitches), non-string elements are stringified and trimmed, duplicates are deduplicated, and the kept pitches are ordered by their position in the available set (not submission order). `resolvePitchSelectionState(storedPitches, available)` implements the first-derivation semantics: when `storedPitches` is null or an empty/whitespace string, all available pitches are preselected and `isFirstDerivation` is true; otherwise the stored selection is parsed, filtered to only pitches in the available set (so a stored pitch no longer available after an upstream change is dropped), and returned in available-set order. A stored narrowed selection is never re-expanded. After an Issue 11 clear (which sets `selectedPitches` to null), the next render is again a first derivation. Both functions are pure: no DB, no side effects, no mutation, no throws. Exports `PitchSelectionFailure`, `PitchSelectionState`, `TWO_HAND_MINIMUM_MESSAGE`, `ONE_HAND_MINIMUM_MESSAGE`, `validatePitchSelection`, `resolvePitchSelectionState`.

### duration-selection-validator.ts

Pure functions encoding the Issue 14 duration-selection rules: the offerable duration set per meter, eligibility validation with corrective guidance, the corrective suggestion search, and the first-derivation resolution. `computeOfferableDurations(catalog, meter)` returns the distinct duration tokens that appear in at least one catalog pattern for the meter, filtered to the module's `CANONICAL_DURATION_ORDER` (`W, H, D, Q, R, E` — descending duration); it returns `[]` for an unsupported meter. `validateDurationSelection(submitted, catalog, meter)` normalizes a hostile submitted value to a trimmed `string[]` (a non-array yields an empty array), deduplicates, rejects each unsupported token (field-addressable failure naming the token) and each supported token not offerable for the meter (field-addressable failure naming the token and the meter), rejects an empty kept set with `EMPTY_DURATION_MESSAGE` (`"Select at least one duration."`), and — when the kept set is non-empty but `computeEligibleRhythms` is empty — rejects with a single group-level failure on `'durations'` whose stable corrective message names the duration group, states that no complete measure can be built for the current meter, and names the computed corrective suggestion by display label. The corrective message is built by `buildImpossibleSetMessage(meter, suggestionTokens)` and never enumerates catalog patterns, internal token letters, or line numbers; it exposes only the `DURATION_LABELS` display labels (e.g. `"the eighth duration"` or `"the half and quarter durations"`). On success it returns the kept tokens ordered by `CANONICAL_DURATION_ORDER` regardless of submission order. `computeCorrectiveSuggestion(catalog, meter, selectedTokens)` searches the smallest addition set of offered durations (not already selected) that makes at least one eligible pattern, trying sizes k = 1 upward over canonical-ordered combinations deterministically; it returns `[]` when the selection is already eligible. `resolveDurationSelectionState(storedDurations, offerableDurations)` implements the first-derivation semantics: null/empty/whitespace stored durations preselect every offerable duration with `isFirstDerivation: true`; a stored selection is parsed, filtered to tokens still offerable (so a stored token no longer offerable after an upstream meter change is dropped), returned in offerable order, and never re-expanded (`isFirstDerivation: false`). `loadRhythmCatalog(text)` parse the packaged catalog text defensively (an impossible parse failure yields an empty catalog), and is the shared parse helper used by the notes route. All functions are pure: no DB, no side effects, no mutation, no throws. Exports `DURATION_LABELS`, `CANONICAL_DURATION_ORDER`, `EMPTY_DURATION_MESSAGE`, `DurationSelectionFailure`, `DurationSelectionState`, `computeOfferableDurations`, `computeCorrectiveSuggestion`, `validateDurationSelection`, `resolveDurationSelectionState`, `loadRhythmCatalog`.

### etude-invalidation.ts

Pure functions encoding the Issue 11 dependent-downstream invalidation model. `computeDownstreamInvalidation(stored, submitted)` compares each upstream setup field (key, octaves, meter, measure count, hands) of the submitted `ValidSetup` against the stored `EtudeParams` and returns an `InvalidationPlan` naming the downstream state to clear in the same committed CAS transition as the upstream change: key change clears pitches and split (retains durations); octave-range change clears pitches and split (retains durations); meter change clears durations (retains pitches and split); measure-count change clears nothing downstream; hands change clears split and revalidates the two-hand minimum (switching to both hands with fewer than two stored pitches unconfirms the notes step, retaining the pitch selection). Multiple changes in one submission clear the union of their dependents. `isReviewReachable(params)` is a pure predicate deriving review reachability from the confirmation flags and hand selection — true exactly when `setupConfirmed && notesConfirmed && (hand !== 'both' || splitConfirmed)` — without consulting any stored review flag (none exists; cross-cutting contract section 5). Both functions are pure: no DB, no side effects, no mutation, no throws. Exports `InvalidationPlan`, `computeDownstreamInvalidation`, `isReviewReachable`.

### workflow-version-field.ts

Pure parser for the hidden `workflowVersion` form field (Issue 10). `parseWorkflowVersionField(raw, field)` extracts a non-negative integer from the raw string submitted by a parameter form (setup, notes, split) or an operation POST. A missing, empty, non-numeric, negative, or non-integer value is a field-addressable `ParseFailure` — never a thrown error. Trims surrounding whitespace before validating against `/^\d+$/`. The function is pure (no DB, no side effects) and reusable by every form that carries the workflow version as a compare-and-set token or precondition (Issues 10, 13, 14, 16, 20, 30, 31, 32, 33, 34, 35, 37, 38). The `field` parameter is not hardcoded so the parser can be reused by forms with different field names. Exports `parseWorkflowVersionField`.

### operation-precondition.ts

Pure precondition checker for operation POSTs (generate, render retry, pdf, start-over) — Issue 10. `checkOperationPrecondition(current, submittedWorkflowVersion, capturedEpoch)` verifies the `workflowVersion` precondition and the `aggregateEpoch` check that every operation POST must pass before any lock acquisition, external call, or state change. Parses the submitted version string via `parseWorkflowVersionField`; a missing, non-numeric, tampered, or negative value is treated the same as a stale version — a `version-mismatch` (cross-cutting contract section 3 rule 1). Then compares the parsed version to `current.workflowVersion`; on inequality returns `version-mismatch`. Then compares `capturedEpoch` to `current.aggregateEpoch`; on inequality returns `epoch-mismatch`. Otherwise returns Ok with the parsed workflow version. The workflow version alone is not sufficient because Start Over resets parameters to defaults and a naive version comparison could coincide; the epoch check guards against this. The function is pure: no DB, no side effects, no mutation, no throws. Exports `OperationPreconditionFailure`, `checkOperationPrecondition`.

### setup-validator.ts

Authoritative domain validator for the setup step's five parameters: measure count (4-32 inclusive integer), time signature (one of 2/4, 3/4, 4/4), hand (left, right, both), key (one of the eighteen supported keys), and octaves (one or more values from 2 through 6). Lives in the Music Domain module so the route never trusts submitted values. `validateSetup(input)` narrows untrusted `unknown` values from the form parser and returns `Result<ValidSetup, SetupValidationFailure[]>` — multiple invalid fields are reported together so a student can correct them in one round. Invalid values are never silently coerced into plausible defaults: an empty string, null, undefined, a wrong type, or an out-of-range value is a rejection. The key field is delegated to `validateKey` from `src/lib/key-domain.ts`; the octaves field is delegated to `validateOctaves` from `src/lib/music-domain.ts`, which normalizes arbitrary order and duplicates to one ascending `number[]` and rejects an empty array, null, undefined, a non-numeric element, or an out-of-range element. Exports `MEASURE_MIN`, `MEASURE_MAX`, `SUPPORTED_METERS`, `SUPPORTED_HANDS`, `ValidSetup`, `SetupInput`, `SetupValidationFailure`, `validateSetup`.

### music-domain.ts

Music domain module for octave validation, contiguous range expansion, and the available-pitch derivation with the C7 cap (Issue 7). `validateOctaves(values)` accepts an array of unknown values (typically strings from a multi-value form field), rejects a non-array, null, undefined, an empty array, a non-numeric element, and any element outside 2-6, each returning a typed `OctaveValidationFailure` with `field: 'octaves'`; for a valid array it parses each element to an integer, deduplicates, sorts ascending, and returns the sorted unique `number[]`. `expandOctaveRange(octaves)` derives the contiguous min/max expanded range from the lowest and highest selected octaves (input order does not matter). `deriveScaleRangePitches(key, octave)` returns the eight tonic-to-tonic pitches for a single octave using the key's diatonic spelling from `deriveKeyPitches`, with the octave number incrementing at the B-to-C crossing (e.g. the seventh degree of D major in the octave-4 range is C-sharp5, not C-sharp4). `deriveAvailablePitches(key, octaves)` builds the full available pitch set by expanding the selection, collecting each scale range's pitches (deduplicating boundary tonics), and applying the C7 cap: every octave-7 pitch is removed except C7, and C7 is kept only when C natural belongs to the key. Returns `{ pitches, lowest, highest }` so the setup form can display the expansion and the cap without generating music. Exports `OCTAVE_MIN`, `OCTAVE_MAX`, `OctaveValidationFailure`, `validateOctaves`, `ExpandedRange`, `expandOctaveRange`, `deriveScaleRangePitches`, `AvailablePitches`, `deriveAvailablePitches`, `parseStoredOctaves`. The `parseStoredOctaves(stored)` helper (added in Issue 13) parses the stored `selectedOctaves` comma-separated string into a sorted `number[]`, falling back to `[4]` when empty or unparseable; it is shared by the setup and notes routes so both derive the same available pitches from the same stored octaves.

### key-domain.ts

Key domain catalog and pitch derivation for the setup step (Issue 6). The authoritative source for the eighteen supported keys and their diatonic pitch spellings, per the PRD's "Supported musical domain" section: nine major keys (C, G, D, A, E, F, B-flat, E-flat, A-flat) and nine natural-minor keys (A, E, B, F-sharp, C-sharp, D, G, C, F). No supported key has more than four accidentals. `validateKey(value)` accepts exactly one of the supported keys (after trimming) and rejects anything else — an empty string, null, undefined, a wrong type, an unsupported key, or an over-four-accidental key — returning a typed `KeyValidationFailure` and never coercing to a default. `deriveKeyPitches(key)` returns the seven diatonic pitch names in scale order using the key signature's conventional spelling (flat keys spell flats as flats, sharp keys spell sharps as sharps, no enharmonic duplicates) from a static lookup table; natural-minor keys use the natural minor scale (flat third, flat sixth, flat seventh relative to the relative major), never harmonic or melodic minor. Exports `SUPPORTED_KEYS`, `MAX_ACCIDENTALS`, `KeyValidationFailure`, `validateKey`, `deriveKeyPitches`.

### rhythm-catalog.ts

Rhythm catalog parser, validator, and eligible-rhythm calculation (Issue 12). The authoritative, build-time-packaged source of complete-measure rhythm patterns. The curated catalog at `Notes/all-rhythms.txt` is the hand-maintained source of truth; each supported time-signature heading (`2/4`, `3/4`, `4/4`) is followed by one token sequence per line over the six supported tokens. Token durations are fixed in quarter-note beats: `W` = 4 (whole), `H` = 2 (half), `D` = 3 (dotted-half), `Q` = 1 (quarter), `R` = 1.5 (dotted-quarter), `E` = 0.5 (eighth). Measure lengths are fixed per supported meter: 2/4 = 2, 3/4 = 3, 4/4 = 4 quarter-note beats. `parseRhythmCatalog(text)` is a pure function returning `Result<RhythmCatalog, readonly CatalogDefect[]>`: it validates syntax (supported tokens only, supported headings only), exact measure length for every pattern under its heading, and at least one pattern per supported meter, collecting every defect in one pass. Each `CatalogDefect` names the offending `meter` and the 1-based `line` number so the health check can report the meter and line. Length validation uses exact arithmetic — every duration and measure length is counted in eighth-note units (quarter beats multiplied by 2) and compared as integers, never accumulated floating-point sums with a tolerance, so a pattern of eighths and dotted quarters is judged exactly. Duplicate identical patterns under the same heading are deliberately allowed in the curated file (it is maintained by hand and an accidental repeat must not break the build); the parsed catalog de-duplicates them, preserving first-appearance order, so each distinct pattern appears exactly once and the recency-weighted repeat selection in Issue 24 is not skewed by a curation accident. `computeEligibleRhythms(catalog, meter, selectedTokens)` is a pure function returning the patterns for the given meter whose every token is in the selected set; a selection with no qualifying pattern returns an empty array (never an error and never a thrown exception), and an unsupported meter returns an empty array. Exports `TOKEN_DURATIONS`, `MEASURE_LENGTHS`, `SUPPORTED_TOKENS`, `SUPPORTED_METERS`, `CatalogDefect`, `RhythmCatalog`, `parseRhythmCatalog`, `computeEligibleRhythms`.

### rhythm-catalog-data.ts

Generated build artifact (Issue 12) produced by `scripts/package-rhythm-catalog.ts`, which reads `Notes/all-rhythms.txt` and emits this module exporting the catalog text as the string constant `RHYTHM_CATALOG_TEXT`. The runtime parser in `src/lib/rhythm-catalog.ts` and the health route in `src/routes/build-health.tsx` import this string so the catalog is bundled into the worker at build time with no runtime file-system read. The module is gitignored (like `schema.sql`) because it is regenerated by the `prebuild` npm hook before every `wrangler build`; `Notes/all-rhythms.txt` remains the hand-curated source of truth. Exports `RHYTHM_CATALOG_TEXT`.

### etude-form-parser.ts

Reusable parameter-form parser, not specific to the setup form. Extracts typed raw values from a `FormData` submission, tolerating the hostile shapes of cross-cutting contract section 2 rule 5: an absent field, an empty string, a repeated field (multi-value), an unexpected extra field, and fields in an arbitrary order each resolve to a deterministic accept or field-addressable reject. None of them produces a thrown error, and none is silently coerced. Each caller supplies a `FieldSpec` declaring the expected field names, their target types, and an optional repeated-field policy (`reject` default, or `first-wins`). Two field types are supported: `string` (single-value, governed by the `repeated` policy) and `string-multi` (multi-value, collects all submitted values into a `string[]` in submission order, preserving duplicates and arbitrary order — normalization is the validator's responsibility; an absent field with zero values is a field-addressable failure). The setup form declares the octave field as `string-multi` and the other four fields as `string` with no normalization, so a repeated single-value field is a reject. Designed for reuse by Issues 6, 7, 13, 14, and 16. Exports `RepeatedFieldPolicy`, `FieldSpecEntry`, `FieldSpec`, `ParseFailure`, `RawValues`, `parseParameterForm`.

### canonical-route.ts

Pure resolver mapping an `EtudeParams` snapshot (or `null` when no aggregate exists) to the canonical route for the current workflow state, per cross-cutting contract section 5. Completion is per-step confirmation: defaults pre-populate controls but do not pre-confirm steps. Issue 4 handles the first two rows of the state table — no aggregate and setup-not-confirmed both resolve to `/etude/setup`. Issue 13 adds the notes-step row: when `setupConfirmed` is true and `notesConfirmed` is false, the resolver returns `/etude/notes` (the notes step is one coherent prerequisite — both pitches and durations must be confirmed for it to count as complete, per section 5). Later issues extend the resolver with the split/review/score rows. Exports `resolveCanonicalRoute`.

### safe-redisplay.ts

Pure-function safe-redisplay value shaping module (Issue 8). The single source of truth for the documented redisplay bounds: `MAX_FIELD_ENTRIES` (32), `MAX_VALUES_PER_FIELD` (64), `MAX_VALUE_BYTES` (128), `MAX_ERROR_BYTES` (256), and `MAX_TOTAL_BYTES` (16 KB). `shapeRedisplayPayload(rawValues, fieldErrors)` takes the raw submitted values (`Record<string, string | string[]>` from the form parser) and the field-addressable errors, and produces a `RedisplayPayload` with `safeValues`, `fieldErrors`, and `droppedFields`. Each bound is enforced as a drop, never a truncation: an offending field is removed from redisplay entirely (and its name added to `droppedFields`) rather than being cut into a different value. An invalid value that passes the bounds (e.g. `'abc'` for a numeric field) is redisplayed as-is — it is never coerced into a plausible default. The validation-state repository imports these constants and the shaping function so both modules share a single source of truth. Exports `MAX_FIELD_ENTRIES`, `MAX_VALUES_PER_FIELD`, `MAX_VALUE_BYTES`, `MAX_ERROR_BYTES`, `MAX_TOTAL_BYTES`, `FieldError`, `RawValues`, `RedisplayPayload`, `shapeRedisplayPayload`.

### validation-state-repository.ts

Server-side validation-state store repository (Issue 8). Persists a nonce-keyed, owner-scoped redisplay payload with a 5-minute `expiresAt` TTL in the `etude_validation_state` table. `storeValidationState(db, userId, payload)` shapes the payload via `shapeRedisplayPayload` (applying the documented bounds), generates an opaque cryptographically random nonce, and inserts the record — returning `Result.ok(nonce)` on success or `Result.err` on storage failure so the caller can fall back to a generic corrective error path. `consumeValidationState(db, nonce, userId)` returns the payload for a matching nonce and owner, deletes the record (single-use), and returns `null` for expired, unknown, or foreign-user nonces — all identically, revealing nothing. Re-exports the bound constants and `FieldError` type from `safe-redisplay.ts`. Exports `VALIDATION_STATE_TTL_MS`, `ValidationStatePayload`, `storeValidationState`, `consumeValidationState`.

### validation-state-helpers.ts

HTTP-layer helpers bridging the validation-state repository and Hono routes (Issue 8). `redirectWithValidationState(c, redirectUrl, db, userId, payload)` stores the shaped payload server-side and issues a 303 redirect with an opaque, single-use nonce cookie (`VALIDATION_STATE_NONCE`, HttpOnly, SameSite=Lax, Path=/etude, Max-Age=300). The cookie value is only the opaque nonce — no submitted value, field name, or error text is ever placed in it. On storage failure, falls back to `redirectWithError` with a generic corrective message so the user still sees a 303, never a 500. `consumeValidationStateFromRequest(c, db, userId)` reads the nonce cookie, consumes the server-side record, always sets a Set-Cookie header that deletes the nonce cookie, and returns `Result.ok(payload | null)`. An unknown, expired, already-consumed, or foreign-user nonce all yield `Result.ok(null)` identically. Exports `redirectWithValidationState`, `consumeValidationStateFromRequest`.

### error-summary-focus.ts

Focus-on-load inline script builder for the accessible error summary (Issue 9). `buildErrorSummaryFocusScript(summaryId)` returns a minimal, server-rendered `<script>` element string that resolves `document.getElementById(summaryId)` and, if present, calls `.focus()` on it. The script is guarded so it never throws when the summary is absent (e.g. on a clean step with no validation errors). It contains only the summary id and DOM focus logic — no field name, submitted value, or error text. This is the first and only client-side script in the project; it exists solely to satisfy the issue's "error summary receives programmatic focus on load" acceptance criterion, which cannot be achieved with HTML alone. The script's SHA-256 hash is whitelisted in `ALLOW_SCRIPTS_SECURE_HEADERS` so the CSP permits its execution. Exports `buildErrorSummaryFocusScript`.

## components/

### error-summary.tsx

Shared accessible error-summary component (Issue 9). Renders an `<section id="error-summary" role="alert" aria-labelledby="error-summary-heading" tabindex="-1" data-testid="error-summary">` containing a heading and an ordered list of error entries. Each entry is an `<li>` containing an `<a href="#<controlId>">` link whose `href` resolves to the invalid control's id, so activating the link moves focus to the control. `buildErrorSummaryEntries(fieldErrors, fieldOrder, groupFields)` is the pure entry-builder: it takes the field-addressable errors, the field order (for visual-order sorting), and a group-field map (for multi-value fields like octaves whose error targets the first member control rather than a single input). It deduplicates identical error messages per field, assigns each error a unique anchor id following the `<field>-error-<index>` pattern (supporting multiple errors per field), orders entries by the field's visual appearance, and routes group-field errors to the group's first member control id. The component and entry-builder are shared so future parameter forms (Issues 6, 7, 13, 14, 16) can reuse them per the cross-cutting contract. Exports `ErrorSummary`, `buildErrorSummaryEntries`, `ErrorSummaryEntry`.

## db/

### schema.ts

Drizzle ORM schema for the D1 database. Defines the `user`, `session`, `account`, `verification`, `singleUseCode`, `interestedEmail`, `etude_params`, and `etude_validation_state` tables. The `etude_params` table (added in Issue 4) carries one etude parameter aggregate per owning student: a text primary key, a `userId` column referencing `user.id` with `onDelete: 'cascade'` and a database-level `UNIQUE` constraint, default-value columns (8 measures, 4/4, C major, octave range 4, right hand), `workflowVersion` and `aggregateEpoch` integers, three step-confirmation boolean flags, and `createdAt`/`updatedAt` timestamps. The `etude_validation_state` table (added in Issue 8) stores nonce-keyed, owner-scoped redisplay payloads for invalid form submission redisplay: a text `nonce` primary key, a `userId` column referencing `user.id` with `onDelete: 'cascade'`, a `payload` text column (JSON), and `expiresAt`/`createdAt` integer columns. Exports the table definitions, the `schema` object, and inferred `*Select`/`*Insert` types.

## middleware/

### correlation-id.ts

Generates a UUID v4 per request, stores it on the Hono context (`correlationId`), and sets it on the `X-Correlation-ID` response header after downstream handlers run, so every response — including error responses — carries the identifier. Wired globally as the first middleware in `src/index.ts`. Exports `correlationIdMiddleware` and `CORRELATION_ID_HEADER`.

## routes/

### build-etude.tsx

The authenticated etude workflow entry route and setup-step form, registered in `src/index.ts` with `secureHeaders(STANDARD_SECURE_HEADERS)` and the `signedInAccess` middleware. `GET /etude` loads (or creates) the owner's etude parameter aggregate via `loadOrCreateEtudeParams`, resolves the canonical route for the current workflow state via `resolveCanonicalRoute`, and redirects (303) to it — a freshly created aggregate has no confirmed steps, so the canonical route is `/etude/setup`. `GET /etude/setup` renders the real setup form (`data-testid="etude-setup-form"`) pre-populated with the saved aggregate's values, with native HTML constraints on every control (min/max/step/required on measures, fixed option lists on meter, hands, and key), accessible labels, a hidden `workflowVersion` field, and a derived-pitch display (`data-testid="key-pitches"`) showing the seven diatonic pitch names for the selected key via `deriveKeyPitches`. Since Issue 8, the GET handler also consumes any pending validation-state record from a rejected POST via `consumeValidationStateFromRequest` — when present, safe redisplay values override the committed aggregate values, and field-level errors (`data-testid="<field>-error"`) are rendered near each offending field. Since Issue 9, the GET handler also renders an accessible error summary (`ErrorSummary` component) when there are field errors, with each entry linking to the invalid control's id, and an inline focus script (`buildErrorSummaryFocusScript`) that moves programmatic focus to the summary on load. Each control's `aria-describedby` references both its instructions element and its field-level error elements (using the unique `<field>-error-<index>` anchor id pattern). The octaves field is rendered as a `<fieldset>` with a `<legend>` and each checkbox labelled "Octave N"; a group-level octaves error targets the first member control (`octaves-field-2`) and is associated with the fieldset via `aria-describedby`. The GET route uses `ALLOW_SCRIPTS_SECURE_HEADERS` so the CSP permits the focus script. `POST /etude/setup` parses the submitted form via `parseParameterForm` (tolerating hostile shapes without a 500), validates the four fields (measures, meter, hands, key) via `validateSetup`, loads the current aggregate to obtain the epoch for compare-and-set, and calls `updateEtudeSetup` — on success it redirects (303) back to `/etude/setup` with a success message; on any parse or validation failure it shapes the redisplay payload via `shapeRedisplayPayload`, stores it server-side via `redirectWithValidationState` (Issue 8), and redirects (303) with an opaque nonce cookie — never a 500. On an epoch failure it redirects (303) back with a safe error message. The `SETUP_FIELD_SPEC` declares four expected string fields with no repeated-field normalization, so a repeated field is a reject. `SETUP_FIELD_ORDER` and `SETUP_GROUP_FIELDS` are the single source of truth for field ordering and group configuration, shared between the route and the error-summary entry builder. A signed-out visitor is redirected to sign-in by `signedInAccess`. On an unexpected repository failure the handler delegates to `handleUnexpectedError` so the safe error page renders with a correlation identifier rather than a 500. Exports `buildEtude`.

### build-etude-notes.tsx

The etude notes-step route (Issues 13 and 14), registered in `src/index.ts` with `secureHeaders` and the `signedInAccess` middleware. `GET /etude/notes` renders the two-group notes form (`data-testid="etude-notes-form"`) with a hidden `workflowVersion` field, an accessible error summary, and two submit buttons: an ordinary Save (`data-testid="notes-save-action"`, `name="action" value="save"`) and a Select all (`data-testid="notes-select-all-action"`, `name="action" value="select-all"`). The pitches group renders available pitches derived from the stored key and octave range via `deriveAvailablePitches`/`parseStoredOctaves` with `data-testid="pitch-field-<pitch>"`; the durations group renders the offerable durations derived from the stored meter's catalog patterns via `computeOfferableDurations(catalog, params.timeSignature)` with `data-testid="duration-field-<token>"` and display labels from `DURATION_LABELS` (never token letters). The catalog is parsed once per request via the shared `loadRhythmCatalog(RHYTHM_CATALOG_TEXT)` helper. Pre-selected values come from `resolvePitchSelectionState`/`resolveDurationSelectionState`: first-derivation preselects all available/offerable values when none is stored; a stored narrowed selection is shown as-is and never re-expanded. When a validation-state record from a rejected POST is consumed, the submitted values override the pre-selection for redisplay. Error-summary entries are wired for both groups via `NOTES_FIELD_ORDER = ['pitches', 'durations']` and a group-field map naming each group's first member, so a group-level duration error links into the first `duration-field-*` control. `POST /etude/notes` handles two actions: `save` reads the submitted pitches and durations via `form.getAll`, validates pitches with `validatePitchSelection` and durations with `validateDurationSelection` (the authoritative server rhythm check), and on success persists both halves via `updateEtudeNotes` (the combined CAS save that sets `notesConfirmed: true`) with a 303 redirect; on either validation failure it shapes a single redisplay payload carrying both safe values and all field errors and redirects 303 with validation state, persisting nothing. `select-all` remains pitch-only: it ignores the submitted checkboxes, persists all available pitches via `updateEtudePitches`, and never touches durations or `notesConfirmed` (so the step stays incomplete until a full combined save). On a stale version or epoch the handler redirects 303 with an explanatory error showing the newly current saved state. Exports `buildEtudeNotes`.

### build-health.tsx

The health route for the etude feature, split into two surfaces sharing one validation pass:

- **Anonymous liveness**: returns only `{ healthy: boolean }` — no value names, no resolved values, no binding names, no defect detail, no secrets.
- **Privileged detailed report**: available only to a privileged operator context (gated by `OPERATOR_TOKEN` via the `X-Operator-Token` header) and to the deployment/startup log via `logInfo`/`logError`. Names every defect and includes the resolved `lilypondTimeoutMs`, but still contains no secret values.

The rhythm-catalog health surface is a pluggable `CatalogHealthContribution` type. Issue 12 fills it: `buildCatalogHealthContribution(catalogText)` runs the packaged catalog text (imported from `src/lib/rhythm-catalog-data.ts`) through `parseRhythmCatalog` and maps any `CatalogDefect`s to `ConfigDefect` entries with `valueName: 'rhythm-catalog'` and a `message` naming the offending meter and line. The health route handler passes the resulting contribution to `runHealthCheck` so a malformed catalog makes the aggregate health result unhealthy with defects naming the meter and line, while the anonymous liveness payload still carries only the healthy flag and leaks no defect detail. A healthy catalog yields a healthy contribution with no defects. Exports `runHealthCheck`, `buildAnonymousLiveness`, `buildDetailedReport`, `buildCatalogHealthContribution`, and the `HealthResult` / `CatalogHealthContribution` / `AnonymousLivenessPayload` / `DetailedHealthReport` types.

### build-safe-error.tsx

The safe error page and global unexpected-error handler. `handleUnexpectedError` reads the request's correlation identifier from context, logs `unexpected error` with the identifier and the error name (never the error message, which may contain PII, SQL, stack traces, or service detail), sets the `X-Correlation-ID` header, and renders `renderSafeError` — a generic safe message plus the visible correlation identifier (`data-testid="safe-error-correlation-id"`) and a return-home action. Wired as `app.onError` in `src/index.ts`. Exports `renderSafeError`, `handleUnexpectedError`, `SAFE_ERROR_TESTID`.

### etude-operation-precondition.ts

Test-only operation-POST precondition route (`POST /test/etude/operation-precondition`) added in Issue 10. Exercises the `checkOperationPrecondition` gate that every real operation POST (generate, render retry, pdf, start-over) will call before any lock acquisition, external call, or state change. Requires the `signedInAccess` middleware so it mirrors a real operation POST's universal route requirements. ## Configuration bindings

The etude feature depends on the following bindings declared in `wrangler.jsonc` and typed in `src/local-types.ts`:

| Binding | Type | Purpose |
|---|---|---|
| `PROJECT_DB` | D1Database | Existing D1 binding (authoritative for ownership and artifact reachability) |
| `ETUDE_GEN_STORAGE` | R2Bucket | Private R2 bucket for etude score/PDF artifacts — no public URL |
| `LILYPOND_SERVICE_URL` | string (secret) | Base URL of the external LilyPond engraving service |
| `LILYPOND_API_KEY` | string (secret) | Bearer token for LilyPond service authentication |
| `LILYPOND_TIMEOUT_MS` | string (var) | LilyPond request timeout in ms; defaults to 30,000 when absent |
| `OPERATOR_TOKEN` | string (secret) | Gates the privileged detailed health report |

The R2 bucket is private — no public URL, no user-derived key namespace. The reported LilyPond version is retained only with SVG render metadata for diagnosis; no permanent version string is embedded in the application or the Piece contract. Deployment acceptance checks the service-reported version against the then-current stable release as a human step.
