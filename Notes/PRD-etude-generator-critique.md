# Critique: PRD Etude Generator

## Review scope

This is a requirements-only review of `PRD-etude-generator.md` against the original requirements in `Ideas.md`, following the skeptical-review criteria in `skills/critique-prd/SKILL.md`. It does not break the PRD into implementation issues or tasks.

## Verdict

**Not ready for issue generation.**

The PRD is substantially better organized and more complete than the original brain dump. It preserves most of the intended user flow, generation probabilities, LilyPond integration, authentication boundary, accessibility goals, rate limits, and test expectations. However, several specified flows cannot work as written, and important musical and security requirements remain ambiguous. The most serious problems are:

1. Redirect-based error handling cannot preserve the submitted multi-step or generated-result state as specified.
2. The PDF flow trusts browser-supplied LilyPond source and forwards it to a compiler-like external service.
3. The user's selected durations are not incorporated into rhythm selection.
4. The pitch-generation algorithm can fail to terminate and does not clearly guarantee that output uses only selected notes.
5. Multiple essential domain rules—key spelling, split validity, 6/8 behavior, repetition semantics, and cross-measure continuity—are incomplete.
6. Rate limiting is not defined atomically and does not say which attempts consume the limit.
7. Three open questions affect core architecture and testability and should not be deferred to implementation.

These are requirements defects, not issue-level details. They should be resolved in the PRD first.

## What the PRD does well

- It accurately captures the server-rendered, authenticated, student-only workflow from `Ideas.md`.
- It converts the form sequence into an explicit set of steps and retains the requirement to carry prior answers through hidden fields.
- It records the principal generation constants: 20% repeated bars, 10% rests, the supplied interval weights, and the 25/75 two-hand rhythm rule.
- It establishes a presentation-independent `Piece → Measure → Note` model and separates generation, LilyPond rendering, service access, and SVG sanitization.
- It includes server-side validation, external-call timeouts, separate generation/PDF rate limits, structured logging, and accessibility requirements.
- It names unit and end-to-end test areas rather than leaving verification entirely implicit.
- It explicitly excludes persistence, audio, MIDI, client-side JavaScript, unsupported durations, and unsupported signatures, reducing scope creep.

## Blocking findings

### 1. Redirects lose the state required to recover from errors

The form's accumulated state exists in POST fields. The PRD then requires validation failures to redirect to the current step using only an error cookie (Validation), generation failures to redirect to the summary, and PDF failures to redirect to the result page (External LilyPond service). No mechanism is specified for carrying the validated choices, field-level validation details, generated SVG, or LilyPond source across those redirects.

The PDF failure flow is impossible as written. The result is a direct response to `POST /etude`; it has no stable GET URL or persisted result identifier to which the server can redirect. The PRD also says the piece is ephemeral, while the Internal data structure section says it exists in hidden form fields and the Routes section says only LilyPond code is submitted by the PDF form. These statements conflict.

This also leaves refresh and browser resubmission behavior undefined. Refreshing a direct POST result can regenerate the piece, trigger a duplicate external request, or hit the rate limit.

**Required decision:** define one coherent state and recovery model. For example, render recoverable errors directly from the POST while retaining the submitted values, or introduce signed/server-side transient state and stable result identifiers. State exactly what survives validation, generation failure, PDF failure, refresh, and Back navigation. The chosen approach must remain compatible with the no-client-JavaScript constraint.

### 2. The PDF endpoint accepts untrusted LilyPond source

The result page places generated LilyPond code in a hidden field, and `step=pdf` forwards it to the external `/pdf` service. Hidden fields are entirely user-controlled. Validating that the field is a string or is below a size limit does not prove that it was generated by this application.

This turns the application into an authenticated proxy to a compiler-like service and allows a user to submit arbitrary LilyPond input using the application's bearer credential. Depending on the external service's sandbox, LilyPond features and resource limits, this could enable expensive compilation, unexpected file/include behavior, or abuse of the service. It also breaks the promise that the PDF is of the same score the user saw.

**Required decision:** do not treat raw browser-supplied LilyPond as trusted. Use an opaque server-side result identifier, a signed payload, or a signed canonical `Piece`/generation payload that the server re-renders. Specify authenticity verification, expiration, maximum input/output sizes, and external-service sandbox assumptions. A rejected or expired payload must not consume the PDF rate limit.

### 3. Duration selection is disconnected from rhythm selection

The user selects allowed durations, but the Rhythm Library interface selects from all rhythms for a time signature. Neither Random generation nor Piece Generator says that patterns containing unselected duration tokens are excluded.

Filtering introduces another missing requirement: some choices yield no valid full-measure rhythm. Examples include selecting only whole notes in 2/4 or only dotted-half notes in 4/4. The PRD does not say whether such combinations are blocked on step 2, whether the UI disables impossible durations, or whether the generator synthesizes another rhythm.

**Required decision:** define the eligible-rhythm algorithm and validation. Every emitted duration must be selected by the user, every bar must exactly fill its meter, and the form must reject any selection for which no eligible pattern exists. Specify how the error is attached to the duration fields and how eligibility works for 6/8.

### 4. Pitch generation is not total and may violate selected-note constraints

The PRD says to sample an interval from 0–12 and re-roll until one fits the range. This is an unbounded probabilistic loop. A one-note range can accept only interval 0; malformed or unexpectedly constrained ranges can have no valid sampled target. Even when a semitone distance is geometrically within the minimum/maximum range, adding that distance can land on a pitch the user did not select. The `noteInDirection` interface returns an `AbsoluteNote` without indicating that no selected target exists.

The algorithm should operate on the discrete selected hand range, not merely its numeric boundaries. For each current note, it needs to derive reachable selected targets, weight them by interval distance, normalize the applicable weights, and choose from that finite set. The behavior for a one-note range should be explicit and deterministic.

The PRD also omits an original continuity rule from `Ideas.md`: for bars after the first, generation remembers the last pitched note of the previous bar as the baseline. It does not define what happens when a bar ends in a rest, when an entire bar consists of rests, or when the duplicated bar's last event is a rest.

**Required decision:** specify a finite weighted-selection algorithm over valid selected notes, including one-note ranges, rests, bar boundaries, and fallback behavior. Restore or explicitly reject the source requirement for cross-measure pitch continuity.

### 5. First-note and repeated-bar semantics are contradictory or incomplete

The PRD says 10% of notes **after the first** are rests, then says the first note may be a rest "per the same rules." Those cannot both define the first-note probability. `Ideas.md` permits the initial event to be a rest but does not state its probability.

A "20% duplicate bar" is also underspecified for two hands. The PRD says duplication occurs in the same hand, but a musical bar in the `Piece` contains both hands. Independent per-hand duplication can combine the right hand from one earlier measure with the left hand from another and can bypass the stated 25/75 shared-rhythm rule. It is unclear whether 20% applies once per measure, once per hand, or only after rhythm-sharing decisions.

The added requirement that adjacent rests have different durations is not present in `Ideas.md`. It may be a valid product decision, but its interaction with duplicated bars and measure boundaries is unspecified.

**Required decision:** define the first-event rest probability, whether duplication copies a whole two-hand measure or one hand, the order of random decisions, and whether adjacency rules apply across measure boundaries and inside copied measures.

### 6. Key, pitch, octave, and split-point rules are insufficiently defined

"Keys up to four flats or sharps" does not enumerate the supported major and minor keys. The examples mix spellings such as `Bb` and `D#`, but the PRD does not define enharmonic spelling, natural/harmonic/melodic minor pitch sets, or how pitch names map to LilyPond key signatures. Two implementations can satisfy the words while presenting different notes.

The cartesian product of selected pitch classes and octaves also needs an explicit octave convention and boundary examples, especially around C. It must be clear whether selecting B and C in octave 4 yields B4 and C4 or whether scale-order/octave rollover is expected.

For both hands, the split index must leave at least one absolute note in each hand. The current rule permits a selected range too small to split and does not state the allowed index bounds or UI labels. "At or below the index" is awkward because an index is not a musical split point.

**Required decision:** enumerate supported keys and pitch spellings; define octave numbering with examples; define the exact sorted absolute-note list shown to the user; require at least two distinct absolute notes for both-hand generation; and constrain the split control so both resulting ranges are nonempty.

### 7. 6/8 reuse needs explicit product acceptance

A 3/4 bar and a 6/8 bar contain the same total number of eighth-note units, so reusing patterns can produce mathematically full measures. They are not musically equivalent, however: 6/8 is normally grouped as two dotted-quarter beats, while 3/4 is grouped as three quarter-note beats. Some reused patterns will obscure compound-meter grouping or create syncopated-looking notation.

The PRD calls proper 6/8 rhythm generation out of scope but still presents 6/8 as a supported practice choice. Merely changing the displayed signature does not ensure useful 6/8 practice material.

**Required decision:** either remove 6/8 from the initial supported choices or define acceptable beaming/grouping and identify which 3/4 patterns are valid for reuse. Add renderer acceptance criteria that verify the displayed meter and compound-beat grouping, not just the string `6/8`.

### 8. Rate limiting lacks transactional and charging semantics

`checkAndRecord` implies a read followed by a write, but the PRD does not require the operation to be atomic. Concurrent requests can both pass before either records its timestamp. The proposed unique `(userId, action)` row is reasonable only if it is updated/upserted atomically with the limit check; the PRD leaves that behavior open.

It also does not say whether the limit is consumed:

- before or after local generation;
- when the LilyPond service times out or returns an error;
- when sanitization rejects the SVG;
- when PDF generation fails;
- when a payload is invalid or has been tampered with.

Database failure behavior is undefined, as is cleanup when a user is deleted despite the suggested foreign key remaining an open question.

**Required decision:** define an atomic enforcement operation, timestamp precision and boundary behavior at exactly 60 seconds, failure policy, which attempts are charged, cascade behavior, and response semantics (including whether `Retry-After` is returned).

### 9. The external-service contract is both specified and unresolved

The External LilyPond service section mandates `{ lilypond: string }` and particular success bodies, while Open Questions says the field name and metadata are unknown. Core client work and tests cannot be derived from a contract that the PRD simultaneously declares authoritative and unconfirmed.

The failure contract also lacks limits and validation for:

- malformed success JSON;
- missing or non-string SVG fields;
- incorrect PDF `Content-Type`;
- oversized SVG/PDF responses;
- empty output;
- redirects from the service;
- sanitization producing empty or unusable SVG;
- timeout cancellation and disposal of response bodies.

**Required decision:** confirm and document the actual API before issue generation. Define request and response schemas, status handling, output-size limits, redirect policy, timeout behavior, and the user-safe error categories to expose. State which details are logged and which are never logged.

### 10. SVG sanitization is a goal, not a complete security contract

"Strip scripts, event handlers, and unsafe external references" is not precise enough for an SVG sanitizer acceptance boundary. SVG can contain `foreignObject`, embedded HTML, CSS, URL-bearing attributes, data URLs, animation, links, and resource references. The PRD should define an allowlist or a tested policy, maximum input size, and behavior when sanitization removes required content.

The mandated DOMPurify/jsdom combination must also be verified against the actual Cloudflare Worker runtime and bundle constraints before it becomes a fixed implementation decision. A Node-oriented DOM implementation may not be viable in that environment.

**Required decision:** specify the sanitizer policy and failure behavior, then confirm a runtime-compatible implementation. Tests must include representative SVG attack classes, not only a generic "known-bad" snippet.

## Important incomplete requirements

### 11. Validation requirements need field-level acceptance criteria

"Validate all accumulated fields" is directionally correct but insufficient. The PRD should enumerate cross-field invariants, including:

- integer measure count in the inclusive 4–32 range;
- exactly one supported key, signature, and hand selection;
- at least one pitch, duration, and octave with no duplicates or unknown values;
- selected pitches belonging to the selected key;
- octaves in the inclusive 2–6 range;
- a splittable range and valid split only when both hands are selected;
- omission of split data for a single-hand piece;
- an eligible rhythm after duration filtering;
- bounded and authentic PDF/result payloads;
- rejection of unknown `step` values and unexpected repeated form fields.

It should also define where users are returned when a hidden value from an earlier step becomes invalid and how valid current values are retained.

### 12. PDF download behavior is incomplete

The PRD specifies only `Content-Type: application/pdf`. It should also define `Content-Disposition: attachment` with a safe filename, malformed/empty PDF rejection, maximum download size, cache policy, and whether the PDF response carries a correlation ID. It should state how the same-score guarantee is tested.

### 13. Accessibility behavior conflicts with the no-client-code constraint unless made concrete

The PRD says focus "moves" on normal renders and after redirects without saying how. In a server-rendered no-JavaScript flow, this likely requires carefully placed `autofocus`, fragment targets, or another explicit mechanism. Only one element may receive autofocus, and error-summary focus and first-field focus can conflict.

Related checkbox/radio groups need `fieldset` and `legend`, validation errors need programmatic association with fields, and the error summary should identify and link to invalid controls. The generated score alternative needs a defined reading order and notation format; "listing the notes" can become extremely verbose for 32 measures and two hands.

**Required decision:** define the HTML-only focus mechanism and accessible structure, plus a useful bounded text-alternative format. Add acceptance criteria for keyboard flow, error association, and both single- and two-hand results.

### 14. Logging requirements are too broad and too vague

"Include [a correlation ID] in every structured log line" does not define which events must be logged or at which severity. The PRD should require logs for external-service failures, timeouts, sanitization rejection, unexpected validation/system errors, and rate-limiter storage failures. It should decide whether routine validation failures and expected rate-limit denials are logged.

Logs must not contain bearer tokens, raw LilyPond, raw SVG/PDF data, full form payloads, or user identifiers that violate the no-PII requirement. A correlation ID should be returned or displayed for unexpected failures so support can connect a user's report to server logs.

### 15. Test requirements do not fully prove the stated behavior

A single fixed random source producing a fixed piece does not establish the 20%, 10%, or 25/75 rules. Statistical tests would be flaky; deterministic branch tests require a defined controllable random sequence or stable seeded algorithm and clear random-draw ordering. The PRD leaves that mechanism open.

Missing explicit tests include:

- duration filtering and impossible duration/meter combinations;
- one-note ranges and split boundaries;
- output always belonging to the selected discrete pitch set;
- cross-measure continuity after pitches and rests;
- whole-measure versus per-hand duplication;
- concurrent rate-limit requests and exact 60-second boundaries;
- tampered, expired, and oversized PDF payloads;
- malformed/oversized external responses and PDF failure recovery;
- SVG sanitizer attack classes;
- POST refresh/resubmission behavior;
- authentication expiry during the multi-step flow;
- field-level accessible errors and focus behavior.

The proposed random-seed cookie must never create a production behavior switch controlled solely by user input. Its environment guard and PRNG contract must be settled before tests and implementation are planned.

## General quality issues

- The PRD is overly specific about some implementation details (ULID, exact module signatures, DOMPurify/jsdom) while leaving product-critical behavior unresolved. Requirements and verified architectural constraints should take precedence over speculative interfaces.
- `Routes` contains the typo "re-rendons."
- "All new code follows ... the red-green-refactor TDD cycle" is a process requirement, not a product requirement; it is already governed by `AGENTS.md` and need not substitute for acceptance criteria.
- The CSP discussion is too confident. CSP is defense in depth and does not make unsafe inline SVG safe; sanitizer behavior still needs to stand on its own.
- The PRD says `LILYPOND_SERVICE_URL` is a secret without explaining why. The bearer token unquestionably is a secret; the URL should be classified according to the deployment's actual sensitivity and configuration model.

## Source fidelity summary

Most of `Ideas.md` is represented, but the following source requirement is materially missing:

- Cross-measure pitch continuity: subsequent bars should continue from the last pitched note of the preceding bar.

The following notable behavior is added or resolved beyond the brain dump and should be confirmed as intentional product decisions:

- adjacent rests may not have the same duration;
- single-hand output includes an explicitly visible empty staff;
- 6/8 reuses 3/4 patterns;
- results are direct POST responses rather than stable result pages;
- rate limiting uses a new database table;
- test randomness may be controlled through a cookie;
- the client may resubmit raw LilyPond source for PDF generation.

Some additions are sensible, but several materially affect security, reliability, or architecture and cannot remain assumptions.

## Decisions required before issue generation

1. Choose a state-preservation and error-recovery model for every form and result transition.
2. Replace or authenticate the raw hidden LilyPond PDF payload and define its lifetime and limits.
3. Define rhythm filtering by selected durations and reject impossible combinations.
4. Define finite pitch selection over the exact selected-note set, including one-note ranges and cross-measure continuity.
5. Define first-rest probability, two-hand duplication scope, adjacency boundaries, and random-decision order.
6. Enumerate keys and spellings; define octave semantics and valid split-point bounds.
7. Decide whether 6/8 is truly supported and, if so, define acceptable grouping and beaming.
8. Define atomic rate-limit behavior and which successful or failed attempts consume each limit.
9. Confirm the external LilyPond API and specify complete request, response, timeout, redirect, and size contracts.
10. Define and validate a Worker-compatible SVG sanitization policy.
11. Enumerate cross-field validation rules and state-retention behavior.
12. Complete PDF download, accessibility, logging, and error-correlation requirements.
13. Resolve the random-injection mechanism and expand deterministic and adversarial test acceptance criteria.

Until these decisions are incorporated, issue generation would force implementers to make incompatible product and security choices independently.
